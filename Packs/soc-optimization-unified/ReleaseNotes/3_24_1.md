##### SOCCommandWrapper

A static argument no longer keeps a dispatch alive after the identifying argument
has been dropped.

The emptiness guard asked whether *any* resolved argument was non-empty. Literal
arguments satisfied that test, so an action whose context reference resolved empty
still dispatched — with the identifier silently removed by the arg-dropping step
immediately below it.

Seen on `soc-enrich-user` against Microsoft Graph User, where
`properties=displayName,...` is a static literal and
`user=${SOCFramework.Artifacts.Identity.User.UPN}` resolved empty on alerts
carrying no identity artifact. `msgraph-user-get` fired with no user, and Graph
rejected the malformed path with
`Unexpected segment DynamicPathSegment. Expected property/$value`.

Only context references now count toward "is there anything to act on" — a literal
carries no evidence and cannot vote. Actions with no context-derived arguments at
all, such as `soc-star-case` with `starred=true`, are unaffected and still dispatch.

The skip record and War Room line now name which arguments resolved empty, so the
reason is visible without reading context.

These were being recorded as integration failures. They are missing evidence, and
should not count against integration health.
