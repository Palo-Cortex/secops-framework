#### Lists

##### SOCFrameworkActions_V3

`soc-enrich-endpoint` now looks CrowdStrike devices up by agent ID instead of
hostname.

```
before   cs-falcon-search-device  hostname = ${SOCFramework.Artifacts.Endpoint.Hostname}
after    cs-falcon-search-device  ids      = ${SOCFramework.Artifacts.Endpoint.AgentID}
```

`Endpoint.Hostname` is populated from the issue's `hostname` field, which on at
least one production tenant carries a fully-qualified name
(`host.sub.example.com`). Falcon stores the short name, so the lookup matched
nothing — and in some cases returned `code: 400 - reason: Bad Request` rather
than an empty result. Endpoint enrichment was therefore returning no device at
all for CrowdStrike-sourced alerts.

The agent ID is exact, already carried on every CrowdStrike alert, and verified
against a live tenant:

```
!cs-falcon-search-device ids=<aid>   ->   Devices: ID, Hostname, OS, Status: normal
```

`ids` is deliberately passed as a scalar. On `cs-falcon-search-device` it is not
declared `isArray` — unlike `cs-falcon-contain-host`, where it is — so it expects
a comma-separated string. Passing a list would serialise as `"['<aid>']"` and
build a malformed filter.

`hostname` is not kept as a second argument: the integration ANDs its arguments
into one filter, so a wrong hostname would continue to suppress the match. When
no agent ID is present the action now skips cleanly via the empty-argument guard
added in 3.24.1, rather than running a lookup that cannot succeed.

This also aligns the branch with the Cortex Core - IR branch of the same action,
which already resolves `Endpoint.AgentID`, and with the 25 other CrowdStrike
actions that act on the agent ID.

Endpoint status matters beyond enrichment: `Status` and isolation state are what
populate `already_contained`, which the assessment reads and the closure policy
gates on.
